1. Ce qu'est une live class dans le code

Le backend ne connaît pas le mot "live class". Le front construit ce concept à partir de deux champs du cours et de deux routes.

À retenir. "Retirer les live classes" veut dire retirer la découverte et l'achat des cours professor_led, pas le lecteur. Le lecteur est commun et reste tel quel.

2. Carte des surfaces

Chaque ligne est un endroit où un utilisateur peut voir ou atteindre une live class aujourd'hui. Le filtre par groupe montre ce qui compte pour chacun.

Ce que la carte ne montre pas et qui rassure : le header, le footer et la page d'accueil ne contiennent aucun lien vers les live classes. L'accueil redirige vers /my-courses ou /learn-anytime. La route /courses redirige vers /learn-anytime, qui filtre déjà strictement sur self_paced.

À retenir. La découverte tient à un item de sidebar et une page. Les fuites restantes convergent toutes vers la page cours : c'est là que se place la garde.

3. Les trois groupes, avant et après

À retenir. Le seul groupe qui demande du soin est l'acheteur, et son chemin dépend de trois choses déjà en place : la ligne de progression créée au paiement, la section dédiée de /my-courses, et le catalogue global non filtré.

4. Le parcours de l'acheteur, étape par étape

Chaque étape est vérifiée dans le code. L'étape orange est le seul point fragile.

Deux vérifications supplémentaires faites sur ce chemin :

  • Langue. getCoursesQuery garde un cours si sa langue est celle de l'interface ou sa langue d'origine (get-courses.ts:77). Un acheteur qui change de langue retrouve donc son cours.
  • Archivage. Le cours archivé reste dans le catalogue et my-courses le garde s'il est en cours (my-courses/index.tsx:50). La fin de la session n'efface pas l'accès.
  • Accès au contenu. Le lecteur vérifie requiresPayment && !isCoursePaid via getPayments (_$courseSlug.tsx:39), jamais le format. Rien à changer.

À retenir. Le chemin acheteur est déjà complet. Le travail consiste à ne pas le casser, pas à le construire.

5. La garde centrale sur la page cours

Une seule règle, placée dans $courseName-$courseId.tsx, ferme la recherche, la page professeur et les URL directes. Elle ne s'exécute qu'une fois les données chargées.

Détail de synchronisation : pour un utilisateur connecté, payments et userCourseProgress arrivent après course. La garde attend isFetched des deux requêtes quand isLoggedIn, et redirige tout de suite sinon. Sans cela un acheteur verrait une redirection avant que son paiement soit connu.

Le lecteur de chapitre n'a pas besoin de garde supplémentaire : pour un cours payant, needsAccess bloque déjà les requêtes de contenu. Pour une live class gratuite, l'utilisateur non inscrit pourrait encore ouvrir un chapitre par URL. C'est une fuite mineure, notée en option dans le plan.

À retenir. Une condition de dix lignes, au même endroit que courseHasToBePurchased, remplace trois filtres backend.

6. Options, du plus petit au plus complet

Supprimer le bloc SideBarItem lignes 150–160.

  • Diff de 11 lignes.
  • Zéro risque pour l'acheteur.
  • Les pages restent accessibles par URL, recherche, page professeur, lien retour.
  • Un anonyme peut toujours acheter.

B · Sidebar + redirections + garde recommandé · 5 fichiers

A, plus un loader de redirection sur /live-classes et /programs, la garde de la section 5, et le lien retour vers /my-courses.

  • Ferme toutes les fuites front identifiées.
  • Aucun changement backend, aucune migration, aucun changement d'API.
  • Réversible par un revert du commit.
  • Les fichiers restent en place : le test -utils.test.ts continue de passer.
  • La garde ajoute une dépendance temporelle sur deux requêtes.
  • Les résultats de recherche montrent encore le titre avant redirection.

C · B + filtres côté API 2 fichiers backend

Exclure professor_led de l'index de recherche (search.ts:24) et de getProfessorCourses.

  • Les live classes disparaissent aussi des résultats.
  • Contredit le brief "backend intact".
  • Une page professeur avec seulement des live classes devient vide.
  • Plus large à tester.

D · B derrière un flag d'environnement 6 fichiers

Ajouter VITE_LIVE_CLASSES_ENABLED dans env.ts et conditionner chaque changement.

  • Réactivation sans déploiement de code.
  • Aucun mécanisme de feature flag n'existe ; seul isPearApp est un précédent.
  • Trois branches conditionnelles de plus à maintenir.
  • Un revert git fait le même travail si le retour n'est pas planifié.

Décision. B. Si un retour des live classes est déjà daté, D vaut le coût ; sinon un revert suffit.

7. Plan d'implémentation par fichier (option B)

Détails · esquisse de la garde 
const isLiveClass = course?.teachingFormat === TeachingFormat.ProfessorLed;
const accessResolved = !isLoggedIn || (isPaymentsFetched && isProgressFetched);
const hasAccess = isCoursePaid || (userCourseProgress?.length ?? 0) > 0;

useEffect(() => {
  if (!isFetched || !course || !isLiveClass || !accessResolved) return;
  if (!hasAccess) navigate({ to: '/learn-anytime', replace: true });
}, [isFetched, course, isLiveClass, accessResolved, hasAccess]);

Les deux isFetched viennent des useQuery déjà présents lignes 134 et 142. isCoursePaid existe ligne 148.

Détails · ce qu'on ne touche pas, et pourquoi
  • my-courses/index.tsx : la section "Live classes" est le chemin de l'acheteur. Le titre navbar.liveClassesTitle peut rester.
  • providers/context.tsx et content.getCourses : filtrer ici casserait l'étape 4 du parcours acheteur et la page professeur.
  • Clés i18n : 11 clés courses.liveClasses.* et 2 clés navbar.liveClasses* dans 20 fichiers de langue. Les laisser évite un diff massif et un conflit avec le pipeline de traduction.
  • Lecteur, vidéo BBB, examens, dashboard professeur : logique métier des sessions live, nécessaire aux acheteurs et aux enseignants.
  • Calendrier et tickets : requêtes userSpecific, donc déjà limitées à ce que l'utilisateur a réservé.
Détails · fuites mineures laissées ouvertes en B
  • Un chapitre d'une live class gratuite reste ouvrable par URL par un non-inscrit. Correction possible dans _$courseSlug.tsx avec la même règle, +8 lignes.
  • Le titre d'une live class apparaît dans les résultats de recherche avant la redirection. Correction en C seulement.
  • Les quatre deep links hardcodés de programs/index.tsx vers des cours plan-*-program-* deviennent inaccessibles avec la page, donc sans effet.

À retenir. Quatre fichiers réels, un fichier généré inchangé. Le gros du diff est de la suppression.
